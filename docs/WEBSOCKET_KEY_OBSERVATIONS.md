# Original WebSocket key input observation

The key-generator routine at0x824d0 has not been reconstructed or credited.
Inspection of its original instructions shows that it saves incoming x24 at
stack offset0x40, writes eight generated bytes at0x38, then builds the sixteen-byte
vector passed to Base64 from the first generated byte and the following
fifteen stack bytes at0x39..0x47. The latter
eight bytes therefore come from that saved caller register.

`tools/observe_websocket_key_prefix.py` executes the original prefix up to the
encoder call while varying four synthetic time values and three incoming x24
values. All12 observations confirm that encoder input bytes8..15 equal the
little-endian incoming x24 value. The first eight bytes reflect two masked
linear-congruential values derived from time. The receipt is
`progress/websocket_key_prefix.json`.

This explains Ghidra's previously unexplained incoming-register value. It
would be incorrect to reconstruct this as sixteen independently generated
random bytes. The evidence establishes machine-level behavior for these
inputs; it does not recover the original C++ expression or establish whether
the behavior arose from an out-of-bounds source read. No entropy, security,
or portability conclusion about the whole application is made here.

The fixture stops before the Base64 encoder, so it is not a full generator
comparison. Tick conversion and allocation are synthetic, and only selected
representable time values are covered. It adds no exact-match credit.

```powershell
python tools/observe_websocket_key_prefix.py --original <private-elf> --clang8 <clang++.exe> --build-dir <scratch-directory>
```
